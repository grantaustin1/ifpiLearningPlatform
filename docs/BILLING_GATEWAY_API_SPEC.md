# ERP360 Billing Gateway API — Contract Specification

> **Status: DRAFT v0.1 — for joint review (ERP360 + IFPI). No implementation exists yet.**
> **This is a design document only. Nothing in this spec changes ERP360 runtime behavior,
> and no implementation work begins before the production go-live cutover.**
>
> Related: `IFPI_INTEGRATION_HANDOFF.md` (§6 HMAC spec, §7 dual-mode addendum),
> `memory/IFPI_GOLIVE_CHECKLIST.md` (item A5), `ERP360_BOLT_ON_WORK_LIST.md` (P2.1).

---

## 1. Purpose & design principles

ERP360 exposes its billing and payment-gateway stack (PayFast card payments,
QLink debit-order mandates, lite-billing subscriptions, dunning) as a
**productized, versioned API** that sibling applications consume the same way
they would consume Stripe or PayFast directly.

**Principles (agreed in §7 dual-mode addendum):**

1. **Consumer-agnostic.** Nothing in this API is IFPI-specific. Any sibling app
   with a gateway token can use it. IFPI is simply the first consumer.
2. **Provider pattern on the consumer side.** The consumer (IFPI) implements
   this API behind its own billing abstraction (`billing_mode: native_stripe | erp360`,
   their B2 work item). The consumer's core product must function fully when
   ERP360 is unreachable — only the payment moment itself may block, and it
   must fail gracefully with retry.
3. **No shared database, no shared code.** Integration surface = this HTTP
   contract + signed webhooks. Ever.
4. **Per-org opt-in, per-org kill switch.** Connection is configured per
   `org_slug`. Disconnecting reverts the org to standalone billing with no
   data migration (consumer keeps its own copy of every record it needs).
5. **Versioned from day one.** All routes live under
   `/api/v1/billing-gateway/`. Breaking changes = `/api/v2/`, never mutation
   in place (same rule as §6.3).

## 2. Authentication

### 2.1 Gateway token (server-to-server)

- ERP360 mints a per-consumer, per-org **gateway token** in its admin
  (Platform Admin → Integrations → Billing Gateway). Opaque bearer token,
  256-bit, prefix `bgw_`.
- Sent as `Authorization: Bearer bgw_...` on every request.
- Scopes (subset grantable): `billing:checkout`, `billing:subscriptions:read`,
  `billing:subscriptions:write`, `billing:refunds`, `billing:customers`.
- Tokens are org-bound: a token minted for `flexgym-demo` cannot touch another
  org's data. 401 on unknown token, 403 on scope/org mismatch.
- Rotation: two tokens may be active simultaneously (rotate without downtime).
  90-day rotation policy, same as the shared secrets.

### 2.2 Webhooks back to the consumer

Signed exactly per the pinned HMAC spec (§6.3 of the handoff doc):
HMAC-SHA256 over raw body bytes, hex, `sha256=` prefix, headers
`X-ERP360-Signature`, `X-ERP360-Event`, `X-ERP360-Event-Id` (dedupe key),
`X-ERP360-Timestamp` (consumer SHOULD enforce ±5 min). Secret:
`BILLING_GATEWAY_WEBHOOK_SECRET` (per consumer, distinct from the IFPI
user-sync secret). Delivery semantics identical to the existing outbound
queue: 2xx acknowledges; retries at 60s/300s; dead-letter after 3 attempts;
manual re-queue possible; consumer idempotency on event_id is mandatory.

## 3. Resources & endpoints

All under `POST|GET /api/v1/billing-gateway/...`. All responses JSON.
All mutating endpoints require an `Idempotency-Key` header (UUID); replays
return the original result with `"idempotent_replay": true`.

### 3.1 Customers

Links a consumer-side account to an ERP360 person (creates one if needed).

```
POST /api/v1/billing-gateway/customers
{
  "external_ref": "ifpi-user-4711",          // consumer's stable user id (required, unique per org)
  "erp360_person_id": 9,                     // optional — link to existing person (from SSO sub)
  "email": "learner@example.com",
  "name": "Emma Sales"
}
→ 201 { "customer_id": "bgc_...", "erp360_person_id": 9, "created": true }
```

- If `erp360_person_id` is provided it must belong to the token's org (403 otherwise).
- If omitted, ERP360 creates a lightweight person record (lifecycle: BILLING_ONLY)
  so gateway usage never pollutes member/lead pipelines.
- `GET /customers/{customer_id}` returns current state.

### 3.2 Checkout intents (one-off payments)

```
POST /api/v1/billing-gateway/checkout-intents
{
  "customer_id": "bgc_...",
  "amount": 49900,                            // integer minor units (cents)
  "currency": "ZAR",
  "description": "IFPI Pro course bundle",
  "external_ref": "ifpi-order-8812",          // consumer's order id (idempotency aid)
  "success_url": "https://ifpi.app/billing/success?order=8812",
  "cancel_url":  "https://ifpi.app/billing/cancelled?order=8812",
  "metadata": { }                             // opaque, echoed back on webhooks (≤4KB)
}
→ 201 {
  "checkout_intent_id": "bci_...",
  "status": "REQUIRES_PAYMENT",
  "checkout_url": "https://<erp360>/pay/bci_...",   // consumer redirects the browser here
  "expires_at": "2026-08-01T10:00:00+00:00"
}
```

- The consumer redirects the user's browser to `checkout_url`. ERP360 owns the
  hosted payment page and the PSP interaction (PayFast today; PSP choice is an
  ERP360 implementation detail the consumer never sees).
- Statuses: `REQUIRES_PAYMENT → PROCESSING → SUCCEEDED | FAILED | EXPIRED | CANCELLED`.
- `GET /checkout-intents/{id}` for polling; webhooks are the primary signal.
- Maps internally to the existing `PaymentIntent` + instant-pay/PayFast flow —
  reuse, not rebuild.

### 3.3 Subscriptions (recurring)

```
POST /api/v1/billing-gateway/subscriptions
{
  "customer_id": "bgc_...",
  "plan": {
    "external_ref": "ifpi-plan-pro-monthly",
    "amount": 29900, "currency": "ZAR", "interval": "MONTH",
    "name": "IFPI Pro Monthly"
  },
  "collection_method": "DEBIT_ORDER" | "CARD",
  "start_date": "2026-09-01",
  "success_url": "...", "cancel_url": "...",
  "metadata": { }
}
→ 201 {
  "subscription_id": "bgs_...",
  "status": "PENDING_MANDATE",
  "mandate_url": "https://<erp360>/mandate/bgs_..."   // hosted mandate/consent flow when DEBIT_ORDER
}
```

- `DEBIT_ORDER` rides ERP360's QLink mandate flow (hosted consent + 2FA);
  `CARD` rides tokenized recurring card via the PSP.
- Statuses: `PENDING_MANDATE → ACTIVE → PAST_DUE → SUSPENDED → CANCELLED`.
  Dunning/arrears logic is ERP360's — the consumer only reacts to status webhooks
  (their §7.1 entitlement layer decides what `PAST_DUE` means for product access).
- `POST /subscriptions/{id}/cancel` `{ "at_period_end": true|false }`.
- `GET /subscriptions/{id}` and `GET /subscriptions?customer_id=` for reads.

### 3.4 Refunds (phase 2 — spec'd for completeness, not in first cut)

```
POST /api/v1/billing-gateway/refunds
{ "checkout_intent_id": "bci_...", "amount": 49900, "reason": "..." }
→ 202 { "refund_id": "bgr_...", "status": "PENDING" }
```

Rides ERP360's existing refund service including its approval workflow —
a refund may sit in `PENDING_APPROVAL` and resolve via webhook.

## 4. Webhook events (ERP360 → consumer)

Sent to a consumer-registered URL (per org, configured alongside the token).

| Event | Fires when |
|---|---|
| `checkout.succeeded` | Payment captured |
| `checkout.failed` | Payment failed/declined |
| `checkout.expired` | Intent expired unpaid |
| `subscription.activated` | Mandate signed / first collection OK |
| `subscription.payment_succeeded` | Recurring collection OK |
| `subscription.payment_failed` | Collection failed (includes attempt count) |
| `subscription.past_due` | Entered dunning |
| `subscription.suspended` | Dunning exhausted |
| `subscription.cancelled` | Cancelled (by consumer, ERP360 staff, or system) |
| `refund.completed` / `refund.failed` | Refund resolution |

Payload envelope (mirrors the user-sync contract):

```json
{
  "event": "subscription.payment_succeeded",
  "event_id": "uuid4",
  "occurred_at": "ISO-8601 UTC",
  "org_slug": "flexgym-demo",
  "data": {
    "subscription_id": "bgs_...",
    "customer_id": "bgc_...",
    "external_ref": "ifpi-plan-pro-monthly",
    "amount": 29900, "currency": "ZAR",
    "metadata": { }
  }
}
```

**Consumer obligations:** 2xx fast (enqueue, don't process inline), idempotency
on `event_id`, tolerate out-of-order delivery (check `occurred_at`), and treat
webhooks as the source of truth over redirect query params (`success_url` is UX
only, never entitlement-granting).

## 5. Error model

Standard envelope (matches ERP360 conventions):

```json
{ "detail": { "error": { "status": 402, "code": "PAYMENT_DECLINED", "message": "...", "request_id": "..." } } }
```

| HTTP | Codes |
|---|---|
| 400 | `VALIDATION_ERROR`, `UNSUPPORTED_CURRENCY` |
| 401/403 | `INVALID_TOKEN`, `SCOPE_MISSING`, `ORG_MISMATCH` |
| 402 | `PAYMENT_DECLINED` |
| 404 | `NOT_FOUND` (org-scoped — never leaks cross-org existence) |
| 409 | `IDEMPOTENCY_CONFLICT` (same key, different body) |
| 422 | `INVALID_STATE` (e.g., cancel an already-cancelled subscription) |
| 429 | rate limited (gateway-class budget, per token) |
| 503 | `GATEWAY_UNAVAILABLE` (consumer should back off + retry) |

## 6. Standalone ↔ bolted-on semantics (per org)

- Consumer keeps `billing_mode` per org. Switching **to** `erp360` = mint token,
  register webhook URL + secret, start creating new checkouts/subscriptions here.
- Switching **away** (kill switch): consumer stops calling the API; existing
  ERP360 subscriptions are cancelled via `POST .../cancel` (or left to run out
  the period). ERP360 retains its financial records (ledger integrity);
  the consumer retains its own copies from webhooks. **No data migration in
  either direction.**
- Mid-flight consistency: the consumer must persist `subscription_id`/
  `checkout_intent_id` + last webhook state locally, so a mode switch or ERP360
  outage never blocks reads.

## 7. Non-goals (explicitly out of scope)

- Shared invoice UI (consumer renders its own billing screens from webhook data
  + GET endpoints).
- ERP360 branching into consumer product pricing logic — plans are opaque
  `external_ref`s to ERP360.
- Cross-app ledger sync or accounting exports (consumer uses its own records;
  reconciliation reports are a possible v1.1 read endpoint).
- Multi-currency settlement (v1: currency passthrough to the PSP; ZAR-first).

## 8. Rollout plan (post go-live only)

| Phase | Scope | Precondition |
|---|---|---|
| 0 | Joint review of this spec; IFPI signs off shapes | — |
| 1 | ERP360: token mint + `customers` + `checkout-intents` + 3 checkout webhooks | **ERP360 production cutover complete + stable** |
| 2 | `subscriptions` (DEBIT_ORDER via QLink first) + subscription webhooks | IFPI B2 entitlement layer landed |
| 3 | Refunds, reconciliation reads, second consumer hardening | Phase 1–2 live for one billing cycle |

**Hard rule: no ERP360 implementation work on this spec before the production
go-live is complete and stable.** This document is the only deliverable until then.

## 9. Open questions for IFPI review

1. Does IFPI need `CARD` recurring at launch, or is `DEBIT_ORDER`-only
   acceptable for phase 2 (SA market)?
2. Webhook receiver URL: one global endpoint with `org_slug` routing, or
   per-org URLs? (ERP360 supports either; per-org preferred for isolation.)
3. Should `customers` auto-link via SSO `sub` when present, making
   `external_ref` optional for bolted-on orgs?
4. Minimum GET/read surface IFPI wants for its billing screens
   (e.g., `GET /subscriptions/{id}/invoices`?).
5. Tax handling: ERP360 emits VAT-inclusive amounts today — confirm IFPI
   renders gross amounts only and never recomputes tax.
